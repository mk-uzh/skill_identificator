# DevSkill

Master's thesis project (University of Zurich): a decision-support prototype that
makes developer skills visible from GitHub and Jira data, and a controlled study of
how team leads rely on its suggestions.

The repository has two parts that meet in a single file:

```
GitHub / Jira  ->  pipeline/  ->  study-data/assessments.json  ->  app/ (study interface)
                   bronze, silver, gold                             Task 1, Task 2, questionnaire
```

* **`pipeline/`** (Python) turns raw repository and tracker data into assessments.
* **`app/`** (Next.js) shows them: Task 1 without support, Task 2 with suggestions that
  can be accepted, adjusted or rejected, with a complete interaction log.
* **`study-data/assessments.json`** is the contract between the two. The interface reads
  it unchanged, so nothing in `app/` needs to be built when the pipeline output improves.

## Quick start (study interface)

```bash
npm install
cp .env.example .env.local     # set STUDY_ADMIN_TOKEN
npm run dev
```

Then open `http://localhost:3000`.

## Participant flow

| Route | Content |
|---|---|
| `/` | Introduction, participant code, consent |
| `/task1` | Empty matrix, no support |
| `/task2` | Matrix pre-filled with task 1 values, one suggestion per cell |
| `/done` | Short questionnaire (trust, confidence, usefulness) |

Other routes: `/overview`, `/summary` and `/developer` (person profile with the evidence).
Ratings use the five-level scale of `model/taxonomy.json` (`l1` to `l5`, plus
`not_observable`).

## Where the data lives

```
study-data/
  assessments.json                 levels, confidence, rationale, evidence per person and competence
  sessions/<sessionId>.json        results: task 1, task 2, suggestions, questionnaire
  events/<sessionId>.jsonl         fine-grained UI events
  interactions/<sessionId>.jsonl   cell log, append only
```

Sessions, events and interactions are excluded in `.gitignore` (data protection).
A different directory can be set with `STUDY_DATA_DIR`, for example a persistent volume.

All reads and writes of study results go through `app/lib/store.ts`. Switching to
Supabase, Postgres or SQLite means replacing the functions there.

### Recorded events

`session_start`, `task_start`, `cell_open`, `cell_change`, `suggestion_shown`,
`suggestion_accept`, `suggestion_dismiss`, `suggestion_modify`, `profile_open`,
`profile_close`, `window_blur`, `window_focus`, `task_submit`, `survey_submit`

Every event carries a timestamp, the milliseconds since task start, the cell, and the
old and new value. Events are sent in batches every four seconds and flushed with
`sendBeacon` when the tab is closed.

## The study script

The suggestions are deliberately scripted, not random. Which cells are right and which
are wrong by design (`veracity`: `correct` / `incorrect`) is a controlled independent
variable; that is what makes automation bias measurable. Today the script is generated
by `tools/make-demo-assessments.mjs`; once gold exists, the pipeline output is frozen and
the cells with deliberately falsified values are marked on top of it. The target value of
a suggestion is computed in `app/lib/suggestions.ts` relative to the participant's own
Task 1 rating, so every suggestion visibly deviates from it.

Regenerate the placeholder (seeded, output is identical on every run):

```bash
node tools/make-demo-assessments.mjs
```

## Export for the analysis

```
GET /api/export?token=<STUDY_ADMIN_TOKEN>&type=interactions  # cell log (default)
GET /api/export?token=<STUDY_ADMIN_TOKEN>&type=ratings       # one row per cell and task
GET /api/export?token=<STUDY_ADMIN_TOKEN>&type=suggestions   # one row per suggestion incl. decision
GET /api/export?token=<STUDY_ADMIN_TOKEN>&type=sessions      # overview incl. questionnaire
GET /api/export?token=<STUDY_ADMIN_TOKEN>&type=events        # fine-grained UI event log
GET /api/export?token=<STUDY_ADMIN_TOKEN>&type=raw           # everything as JSON
```

The CSV files are in long format and can be read directly into R, SPSS or pandas.
`suggestions` contains `followedSuggestion` (0/1), `veracity` and `timeToDecisionMs`.

Test the export before real participants exist:

```bash
npm run seed
```

## Pipeline

```bash
cd pipeline
pip install -r requirements.txt
cp .env.example .env
```

Run the notebooks in the order given in [`pipeline/README.md`](pipeline/README.md).
Bronze data, the identity mapping and the repository clone stay on the machine and are
not versioned.

`npm run ingest` and `npm run infer` belong to the replaced TypeScript pipeline in
`legacy/` and write demo data, not pipeline output.

## Deployment

On Vercel and similar serverless platforms the file system is ephemeral, so the
file-based store only works there for local testing. For real participants either run on
a server or container with a persistent volume (set `STUDY_DATA_DIR`) or switch
`app/lib/store.ts` to a database. Next.js 14.2.15 has a reported vulnerability; update
before deploying.
